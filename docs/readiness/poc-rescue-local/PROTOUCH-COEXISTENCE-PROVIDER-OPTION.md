## Direct-app verification under the current constraints

Meta's current [Coexistence onboarding documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users/) requires the integrator to be an existing Solution Partner or Tech Provider and to use Embedded Signup with session logging. No documented exception was found for a business that merely owns a separate Meta app. This is the published onboarding requirement, not proof that every unpublished account-specific arrangement is impossible.

Meta separately supports [direct-developer System User tokens](https://developers.facebook.com/documentation/business-messaging/whatsapp/access-tokens) for owned or shared business assets and [app subscriptions to WABA webhooks](https://developers.facebook.com/documentation/business-messaging/whatsapp/reference/whatsapp-business-account/subscribed-apps-api). Those documents establish asset access and event subscriptions; they do not establish an alternative Coexistence onboarding flow or prove that the existing ProTouch credential can activate its pending number while preserving the phone app.

[Callback overrides](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/override) can route messages, history, contact sync and phone-app echoes to another endpoint. Account lifecycle events including `account_update`, `account_review_update` and `account_alerts` remain at the subscribing app's default callback. An override therefore does not, by itself, establish complete account-lifecycle delivery or transfer the application's signing-secret ownership to ProTouch. Any future external-provider arrangement must explicitly verify those boundaries before activation.

**No supported free direct-app Coexistence onboarding route was verified under the user's current constraints.** The current separate ProTouch app and pending phone record are insufficient. No provider subscription, app conversion, callback change, new registration attempt or phone-app removal was performed in this investigation.

## Required integration

The documented 360dialog messaging API uses `https://waba-v2.360dialog.io/messages` with a per-number `D360-API-KEY`, rather than the existing ProTouch app's Graph token. Templates use its `/v1/configs/templates` API. A provider-specific implementation must preserve current before-attempt authorization, the durable outbox and ambiguous-send fences. Sources: [send messages](https://docs.360dialog.com/partner/get-started/quickstarts/send-a-message), [templates](https://docs.360dialog.com/docs/resources/templates).

Its customer webhook is configured through `/v1/configs/webhook`, with custom authentication headers supported. The existing Meta endpoint requires an HMAC generated from the configured Meta app secret. That endpoint cannot simply accept these provider deliveries: a separate authenticated provider boundary must retain exact WABA/phone/tenant binding and durable deduplication. A static provider secret must never be mislabeled as a verified Meta HMAC or silently mint the existing Meta-specific memory proof. Sources: [webhook configuration](https://docs.360dialog.com/docs/messaging/webhook), [API schema](https://docs.360dialog.com/docs/messaging-api/api-reference/webhooks).

**Direct reuse of the existing ProTouch Meta app token/webhook after external onboarding is not established.** The official Meta findings above do not confirm that this exact Coexistence account, token and commercial arrangement would support an independent application. The investigated 360dialog implementation would therefore require its documented provider API and an authenticated integration boundary; no such adapter is authorized or implemented.

Live phone-app echoes go to the phone-number webhook. Contact sync also reaches that webhook once configured. However, the provider documents historical delivery to a partner-configured webhook; **direct clients obtain the synchronized history through a Hub download**. Automatic historical callback delivery on the Regular direct-client plan must not be promised. Before onboarding, choose a supported Hub export/import workflow or obtain explicit provider support for the desired delivery. Imported history must continue to trigger zero automation and must not open the service window. Source: [Coexistence webhook reference](https://docs.360dialog.com/docs/messaging/webhook/webhook-reference).
