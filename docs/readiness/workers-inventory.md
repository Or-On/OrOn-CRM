## Confirmed source findings, prioritized

Each item requires an isolated regression test before a fix may be marked `verified-local`. No application files were changed by this audit.

1. **WRK-001 — high, failed: cross-provider/cross-queue claims.** `db/alembic/versions/66e34e3b2067_add_messaging_worker_claim_primitives.py` creates `ops.claim_inbound_events` without provider or non-null-tenant restriction and grants messaging runtime execute. Dispatcher writes `provider='livekit'`, `tenant_id=NULL` rows to the same table (`oron_dispatcher/webhook_ledger.py`). Messaging's `processInbound` treats every non-status event as WhatsApp, so it can steal/alter retrying or newly inserted voice events and receive unrelated provider payloads. `claim_jobs_all_tenants` likewise accepts arbitrary queue for messaging callers. Fix using successor migration with explicit service/provider/queue allowlists, not a historical edit. Test roles concurrently, including livekit null-tenant payload unreadability.
2. **WRK-002 — high, failed: leases can expire before work starts.** `worker/database.ts:processAvailable` claims 25 jobs with 60s leases and sequentially awaits each. One Meta request may take approximately 25 seconds with retries; AI defaults 20 seconds. Later jobs can be reclaimed by a second worker before the original reaches them. Real send/AI/call branches do not lock/validate the owned job before effects. Use one-at-a-time claims or bounded concurrent claims plus renewal and fencing; verify stale worker cannot send, finalize, or alter another worker's attempt.
3. **WRK-003 — high, failed: queued effects ignore new restrictions.** `loadOutboundWork` updates request from queued/**sending** without checking current contact lifecycle/consent/opt-out, channel/tenant active status, actor membership, service window or AI ownership. `setConversationOwnership` does not cancel already queued AI outbound work; AI generation recheck only protects before queue insertion. Human takeover, deletion or opt-out after queueing can still be followed by an unwanted send. Add final eligibility decision/failure/cancellation and fencing; do not hold DB transactions across provider calls. Test controlled races, queued AI acknowledgements following a intentional handoff, and user replies separately.
4. **WRK-004 — high, failed: ambiguous send retry is not idempotent.** Meta adapter never transmits `idempotencyKey` to a provider-supported deduplication mechanism. It retries network timeouts/errors; worker retries retryable jobs. Provider acceptance followed by lost response/crash may resend. A DB error after successful send is treated as generic processing failure and can leave an accepted message represented failed. Distinguish definite rejection from unknown outcome; persist attempt identity/state and require reconciliation/manual decision for ambiguous acceptance. Do not promise exactly-once Meta delivery.
5. **WRK-005 — medium, failed: outbound idempotency ignores changed payload.** `queueWhatsAppOutbound` returns prior request by tenant/key without comparing requested conversation, recipient, provider, kind or content/template parameters. Same-key conflicting requests must be rejected, not silently return a different successful operation. Add normalized request fingerprint with concurrency-safe admission and retry-safe tests.
6. **WRK-006 — high for multi-sender deployment, failed: global sender at dispatch.** Outbound job remembers channel but `loadOutboundWork` does not return that channel's configuration/credential reference. `main.ts` constructs one Meta adapter from process-wide phone ID/token/version. Queueing via another tenant/channel or editing `.env` before processing can send using the wrong sender. Constrain supported channel to exact configured sender immediately, and document one-sender limitation until tenant-scoped credential resolution is implemented. Never silently send a queued channel via different credentials.
7. **WRK-007 — medium, failed: provider time/status fidelity.** Stored inbound envelope drops provider timestamp, and `ingestWhatsAppInbound` sets customer-service expiry to processing time +24h before message deduplication. Backlogged/replayed events can extend the local window incorrectly; local state can disagree with Meta. Status ingestion always accepts failure regardless of event chronology, and send completion can overwrite a receipt processed immediately after provider acceptance. Preserve trustworthy bounded provider timestamps and monotonic/temporal reconciliation. Test delayed/replayed/out-of-order events. Meta remains final window authority; never bypass it.
8. **WRK-008 — high for customer staging, failed: simulations are not environment-separated.** Control API starts voice simulator job loop with every configured repository and exposes simulation route regardless of environment. Messaging handles simulator jobs alongside real ones; empty manual automation inserts success for a no-op. Keep these as explicit isolated test/dev capabilities, gate admission/execution in staging, ensure analytics excludes simulators or labels provenance. No real traffic is needed to fix this.
9. **WRK-009 — medium, failed: callback frozen version not honored.** `queueWhatsAppAutomaticCall` payload stores flowVersion and validates it; `loadAutomaticCallWork` checks availability but returns no version; `call-provider.ts` posts only flow_id; dispatcher persistence loads latest flow and latest canonical attached prompt. A queued callback may execute newly published behavior. Propagate immutable version identity through contract/persistence/launcher or explicitly document/review latest semantics; preferred fixed version regression.
10. **WRK-010 — medium, failed: real call replay payload/recovery mismatch.** `Dispatcher.place_outbound_call` derives room from tenant/key and returns existing regardless of different destination/flow; `PostgresVoiceRuntime.begin` returns false on any existing session. If startup/SIP failed or process crashed before actual dial, later retry can be reported duplicate success without an actual call. Preserve command fingerprint and explicit lifecycle/reconciliation states; never blindly redial an ambiguous accepted SIP request.
11. **WRK-011 — medium, failed: real voice restart recovery not complete.** `_active` is process-local; `_finalize` returns when room absent. On process restart, room_finished can be acknowledged without finalizing persisted session. Webhook ledger uses constant `locked_by='dispatcher'`, has no fencing token and no independent retry consumer; retries depend on provider redelivery. Add bounded reconciliation/call recovery or block restarts during active calls in staged runbook until implemented. Test two dispatchers and stopped-process/room-finish case.
12. **WRK-012 — medium, failed: artifact read bounds.** `oron_sessions/artifacts.py` reads any file URI / GCS bucket stored on an accessible session, with no configured root/bucket allowlist, byte cap or read deadline; `get_recording` loads entire WAV into memory. Request cannot directly choose URI, which limits exploitability, but compromised persisted URI/large object remains risk. Enforce allowed storage root/bucket and size/time limits, private streaming/range semantics where appropriate. Also LiveKit webhook decodes full unbounded body outside signature error guard. Validate application bounds in addition to proxy limits.
13. **WRK-013 — high for autonomous calls, failed: model decision substitutes for durable consent evidence.** `request_call` JSON decision is the only semantic check that inbound text explicitly requested an immediate callback. Queue admission verifies an inbound text exists but not independent action confirmation. Arbitrary conversation history is untrusted, and latest inbound is chosen when processing rather than pinned per AI job. No tenant-wide spend/token/day-call limit found; 10-minute conversation cooldown is not a spending cap. Model prompt is not enforceable tool authorization. Keep autonomous flags off for staging until robust bounded call-action policy and consent/cost budget tests are complete; preserve supported user-directed flow rather than invent consent.
14. **WRK-014 — medium, failed: shutdown does not drain active worker effects.** `worker.ts` races stop against `processAvailable`, then closes DB while pending work still runs (Promise.race does not cancel it). Stop can arrive while a provider send is in flight, closing pool before acknowledgement persists. Use explicit in-flight drain/cancellation policy with deadline and ambiguous-outcome handling, then close; test signal during pending HTTP and DB completion.
