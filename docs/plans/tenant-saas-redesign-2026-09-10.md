# Tenant application audit and redesign

Status: implemented and locally verified; checkpoint uncommitted and not deployed.

This checkpoint implements the latest **Tenant Application — Full UI/UX Audit & Redesign** brief. It builds on the prior Or-On brand work, but replaces the earlier card-heavy layouts and simulator-oriented tenant controls. It is not a claim of production deployment or regulatory compliance.

Layout decisions: reduce medium/large surface radii to 8/12px, reduce operational spacing and headings, use ledgers/tables and master-detail structures rather than repeated large card grids. Keep the existing Or-On brand palette, bilingual typography, theme support, responsive shell, keyboard controls and semantic focus treatment. Motion is short and purposeful: numerical updates, chart changes and a finite healthy-state pulse; reduced-motion stays immediate.

## Data and safety decisions

- No provider calls, messages, webhook changes, resources or deployments are part of this work. Feature flags remain default-off and provider admissions remain server-enforced.
- The brief explicitly asks to assume permission for contacts added to the platform. New-contact inserts grant permission prospectively; duplicate imports skip rather than overwrite. Manual/API creation rejects existing phone/WhatsApp identities and case-insensitive email matches before inserting, including archived and restricted contacts, so a new channel identity cannot shadow an existing restriction. Existing unknown/revoked states and opt-outs are preserved. No migration or bulk update of existing contacts is authorized by default. A non-blocking question offered the user a choice about existing unknown states.
- Removing tenant consent controls does not remove opt-out enforcement or permit the UI to bypass real-provider confirmation, authentication, tenant isolation or permissions.
- Monthly metrics are read-only aggregates of RLS-visible existing records, from UTC month start through the observation timestamp, not capped UI lists. Future-dated records are excluded. Message delivery uses the current status of messages created in that period, not receipt arrival dates.
- Delivery rate = delivered/read divided by delivered/read/failed; queued/sent/other non-final outbound records are separate. No denominator produces an em dash, not 100%. Contacts reached means distinct recipients with delivered/read outbound messages.
- Session `ended` is not labelled successful or answered. Agent usage events/tokens are not attributed to a profile without attribution data. Flow failures are recorded run outcomes, not provider-health incidents. Retained test records remain included and the scope says so.
- Database verification caught the existing column-level Voice boundary: web may read session IDs/status/time, but not `call_seconds`. The aggregate uses only granted columns. Talk time remains on the existing Voice API; grants were not widened for the dashboard.
- No usage-plan/allowance, projected overage, comparative KPI, provider uptime, persistent incident history, queue latency, notification preference or unsupported configuration is invented.
- Lists explicitly disclose loaded/sampled scope where the API is bounded. Client pagination does not pretend to navigate every server record.
- Health round trip includes browser/application/check transport, not a provider-latency metric. History contains only actual observations during the open page session, with at most 12 samples. Failed refreshes never inherit a fresh healthy claim. The BFF has an eight-second upstream deadline; the browser has a ten-second request deadline. Only enumerated PostgreSQL readiness values are projected, never arbitrary infrastructure metadata. Timeouts retain the previous check explicitly as stale and restore the retry action.
